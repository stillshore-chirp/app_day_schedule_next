# Issue品質ゲート

Issueは作業項目の一覧に加え、第三者が必要性、根拠、期待成果、完了条件を検証できる追跡単位です。

## 1. 適用範囲

repository変更に先立って新規Issueを作成する場合と、既存Issueを主Issueとして採用する場合に適用します。軽微変更でIssueを省略できる条件はroot `AGENTS.md` とGitHub配送Skillを優先します。

## 2. 必須内容

該当する `.github/ISSUE_TEMPLATE/` を使い、少なくとも次を記載します。

1. **背景と判断理由**
   - なぜ必要か。
   - なぜ今対応するか。
   - 対応しない場合に誰がどこで困るか。
2. **根拠と不確実性**
   - 確認済み事実。
   - ユーザーから提示された判断材料。
   - code、official specification、test、log、実データなど公開可能な証跡。
   - 仮説、推定、未確認事項。
3. **現状の問題と影響**
   - 現在の挙動または制約。
   - 利用者、data、sync、notification、platform、運用、保守への影響。
4. **現在と対応後のユーザー体験**
   - 対象ユーザー、利用文脈、達成したいこと。
   - 現在見聞きし、判断し、操作し、待機し、失敗し、回復していること。
   - 対応後に理解、判断、実行、回復できるようになること。
   - ユーザー申告、実ユーザー観察、観測事実からの推定、未確認の仮説の区分。
5. **目的と期待成果**
   - 実装項目の列挙に加え、作業後に成立させる状態。
6. **対応範囲と非対象**
   - 今回行うこと。
   - 今回行わないことと理由。
7. **受け入れ条件と検証方針**
   - 第三者がPass / Failを判定できる条件。
   - 各条件を確認するtest、画面、log、document、manual observation。
8. **riskと未確認範囲**
   - 既存挙動への影響。
   - 実行できない検証。
   - 完了後にも残る不確実性。

## 3. 事実・判断・仮説の分離

| 種別 | 書き方 |
|---|---|
| 確認済み事実 | 何を、どの証跡で確認したかを書く |
| ユーザー提示の判断材料 | 依頼時に提示された情報と、repository側で再確認した範囲を書く |
| 判断 | どの事実、目的、制約から方針を選んだかを書く |
| 仮説・推定 | 未確認であることと、確認方法を書く |
| 未確認事項 | 確認できない理由、影響、次の最短actionを書く |

外部評価や第三者資料は出典だけで確認済み事実へ格上げしません。高riskな判断はcode、test、official specification、実環境の証跡を優先します。

## 4. ユーザー体験

「現在」と「対応後」は同じ対象ユーザーと利用文脈を基準に対で記載します。

### 現在

- ユーザーが達成したいこと。
- 現在の表示、操作、待機、失敗、回復。
- 認識、迷い、負担、安心、信頼の状態。
- 主観を直接確認していない場合の根拠区分。

### 対応後

- 同じ文脈で何が変わるか。
- 新たに、または確実に理解・判断・実行・回復できること。
- 手数や待ち時間と、結果として得られる状態。
- 受け入れ条件へ接続する確認方法。

調査、内部改善、保守、ガバナンスで製品利用者の体験が直接変わらない場合も、その事実と理由を書きます。直接の対象が開発者や運用者である場合は対象を明示します。

## 5. Day Schedule固有のrisk

該当するIssueでは次を明示します。

- local data、Google Calendar / Tasks、Outbox、conflict
- time、timezone、DST、recurrence、cross-midnight
- notification、Focus、sleep / resume
- SQLite schema、migration、backup / restore、legacy import
- Tauri capability、CSP、keyring、installer、macOS / Windows
- accessibility、keyboard、drag equivalent、Compact Window
- public evidence、token、個人予定、diagnostics

すべてを定型的に埋めず、影響する領域と対象外理由を明確にします。

## 6. 既存Issue

既存Issueが作業範囲を含んでいても必須内容が不足する場合は、実装前に本文を更新するか、不足内容をIssueコメントへまとめます。実装中にscope、判断、確認済み事実、未確認事項が変わった場合もIssueを更新します。重要な判断をPRだけへ閉じ込めません。

## 7. 公開安全性

Issueは公開文書として扱います。secret、認証情報、個人予定、raw DB / backup / log、完全なpath、追跡可能なIDを貼りません。

公開できない根拠は、確認した証跡の種別、公開可能な観測事実、判断への影響、公開できない範囲、次の確認へ要約します。詳細は `docs/security-publication-checklist.md` とsecurity-publication Skillを使います。

## 8. Pass / Fail

### Pass

- 理由、根拠、期待成果、範囲、非対象、acceptance、verification、riskを読み取れる。
- 確認済み事実と未確認事項が分離されている。
- 同じ対象ユーザーと文脈について現在と対応後を比較できる。
- 主観に関する根拠区分が明示されている。
- acceptanceが観測可能な結果になっている。
- 公開禁止情報を含まない。

### Fail

- 変更fileや実装項目だけが並び、必要性が分からない。
- 誰の何がどう変わるか説明されていない。
- 未確認の主観、外部情報、仮説を確認済み事実として断定している。
- 現在と対応後で対象ユーザーや利用文脈がすり替わっている。
- 非対象がなくscopeが無制限に広がる。
- acceptanceやverificationがなく、完了を客観判定できない。
- 未確認範囲や残るriskを隠している。
- 公開禁止情報を含む。

FailのIssueを主Issueとして実装を開始せず、必要な判断材料を補います。
